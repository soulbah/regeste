- 2026-07-27 — The measurement loop, and two bugs in the guard that made it necessary. **117: 110 → 111**, and the other three held-out sets unchanged (schedule 13/16, quote 11/14, loan offer 15/16), so the numeric grounding check now costs nothing where it used to cost correct answers. Both bugs were mine and both were general. First, `numberTokens` matched `\d[\d\s.,]*\d` and `\s` also matches a newline, so a PDF table flattened to text — one figure per line — collapsed the column "FIXE\n180,00\n0,00" into the single token 1800000; an answer stating "180,00 euros" then found no support for a figure printed right there in its evidence and was refused. The benchmark oracle already carried a correct number grammar for the same job, so the two had silently drifted; it now lives in `$lib/numbers` and the guard, the citation binder and the oracle share one grammar and one canonical form. Second, the guard refused arithmetic: "12 × 14,91 € = 178,92 €, l'écart est de 6,58 €" and "la différence est de 2 700 € (3 000 € - 300 €)" are correct answers whose figures the document does not print, because they are computed. When an answer shows it is computing, a stated value may now be one arithmetic step over figures the evidence carries, admitted left to right so the gap can lean on the product the same sentence just established — which also refuses arithmetic that does not come out. The licence is keyed to operators and the words for a gap; "total" and "somme" are deliberately excluded, being field names a document prints, so a fabricated total cannot license itself. Verified rather than assumed: replayed over all 117 raw pre-guard answers the guard refuses none, and against the quote case's real evidence (11 passages, 279 numeric operands) the fabricated 18 884,73 € stays refused in both a flat and a gap-worded phrasing. **The harness debt, which is the real story.** Three consecutive guard changes cost three hours to measure because the full run took an hour each — and none of them touched a prompt, since the guard runs after generation. - 2026-07-26 — First held-out set, and what it caught. The 117 are one insurance quote, so nothing in them can say whether the pipeline generalises; the amortization notice (7 pages, a 240-row schedule, a genre the tuning never saw) now has its own 16-case matrix in the local corpus, with three deliberately unanswerable cases. Its first run scored 5/16 with page recall 16/16 — the right page every time, the gate rejecting it anyway — which looked exactly like the overfit the audit predicted. It was not: the oracle could not read a table row. Every digit, space, dot and comma formed one run, so "1 05.11.2025 14 949,07 69,39 50,93 18,46" collapsed into a single 24-digit token and no individual cell was ever visible, even with that exact row returned at rank 2. Fixed by matching one value at a time, ordered so a date wins over a decimal and a thousands group only continues on exactly three digits, which is what separates two amounts from one phone number; long values stay tolerant of any grouping since a document writes "+33 801 840506" as it pleases. A second defect fell out of the same run: digits were compared as strings, so "15 000" missed "15 000,00" and "1,99" missed "1,9900" — amounts are now compared as values with trailing decimal zeros trimmed, dates keeping their digits. Both fixes leave the three archived runs at exactly 111, 109 and 105, so they correct rather than loosen. With a working oracle the held-out set scores **15/16, page recall 16/16, passage hit@1 46.2%, hit@3 92.3%, MRR@10 .692**, against 57.5% / 84.1% / .722 on the corpus the pipeline was tuned on. Worse at rank 1, better at rank 3, comparable overall: the pipeline generalises considerably better than "48 iterations of overfitting" suggested, and that correction matters as much as the failures. The one genuine failure is a real bug, and general: "à quelle périodicité les remboursements sont-ils prélevés ?" retrieves sixteen near-identical schedule rows and never the page-1 line "Périodicité : MENSUELLE", because the header repeated on every schedule page ("Echéancier de remboursement", "Prélèvements sur votre compte") matches the question on all six of them and crowds out the single chunk holding the answer. Any document with a repeated table header will bury a one-off field the same way; there is a per-document quota but nothing caps near-duplicates. Tooling: `bench-ingest.mjs` adds a document through the product's own ingest path, `dump-parsed-document.ts` prints a PDF as the pipeline reconstructs it (cases must be written from what the index contains, not from what a viewer shows), and every scoring tool takes `BENCH_MATRIX` so held-out sets are measured with the same instrument as the dev set. `bun run verify` green (760).
- 2026-07-26 — Core audit acted on, branch `feat/retrieval-core-rework`. The measuring instrument was repaired first, because eight of the intended fixes had "re-run the 117" as their acceptance criterion and that criterion could not be trusted: the generation cache only returned an entry that still satisfied the oracle, so a cached failure re-ran while a cached success replayed — a ratchet the score could only climb. Removed. Answer matching moved from normalized substrings (which found "non" inside "renonciation") to token alignment, keeping prefix tolerance for the oracle's deliberate truncated stems, and reaching past a glued unit so "70" matches "70m²". Every result now records which path produced it (extractive / cached / llm / skipped / no-evidence) and the report decomposes the score by source. Seven query expansions that quoted the benchmark's own gold answers were deleted, including one triggering on `sectoin`, a misspelling the benchmark injects on purpose. Then the cheap correctness fixes: queries were embedded in their normalized form — accents stripped, lowercased — while passages keep full French orthography, so both sides of the dense comparison were in different scripts on every question; vec0 refuses k above 4096 and the KNN budget was unbounded, so a library past ~5 120 chunks with a partial selection threw out of retrieval and the turn produced no answer at all; citation binding compared digit soup, so "page 12, 3 ans" carried the value 123 and an invented number both matched an accident and excluded the passage spelling the value in words; the answerability gate treated every capitalised token as a required acronym, so a question typed in capitals demanded LE, LA and DE appear verbatim; neighbour expansion drew on the candidates' own budget, so each anchor's two neighbours cost two candidate slots and every channel lost ranks 21-60 before fusion; and the assisted request carried each document's filename as its excerpt label, against this repo's own rule and against what the interface tells the user, with the pre-send byte figure not counting it. Four analysis tools were built, three of which need no browser and no model: `rescore-private-run.ts` (replay any archived run under the current oracle), `retrieval-metrics-report.ts` (hit@k, MRR, nDCG at the rank of the answer-bearing passage), `compare-private-runs.ts` (which case moved, through which of the three gates), and `bench-retrieval.mjs`, which drives the existing model-free gate headlessly — 110 seconds against 59 minutes, the loop that was missing. What they measured changed the plan twice. First: re-scoring the four archived runs under the repaired oracle reproduces every one of them exactly (111, 111, 109, 105), so the scoring path was never the leak, and the audit's relayed "36 cases pass on a substring" was a count of potential, not of flips. Second, and larger: across the four runs that carried the headline 105 → 111, passage hit@1 went 58.4 → 57.5 and MRR@10 .727 → .723 — retrieval ranking never moved, and the case-by-case diff agrees from the other direction, five of the six cases gained being RaC → RAC, retrieval already passing and the answer gate flipping. The answer-bearing passage is rank 1 only 57.5% of the time, which the 94.9% end-to-end score cannot see. Cold run of the full 117 with the ratchet gone: 110/117, one case gained, two lost, both `[llm]` with retrieval passing — generation variance made visible, not a regression, and six of the seven surviving failures are generation failures. Finally the audit's own centrepiece was tested and rejected: making the score commensurable (RRF_K 60 → 20, retrieval base normalized per query, the fourteen feature bonuses applied as a bounded multiplier instead of a sum) measured passage hit@5 90.3 → 85.8, MRR .722 → .710, the retrieval gate 117 → 115, and answers buried past rank 5 going 11 → 16.
